## 1.分支
本项目依照 Git Flow 分支模型来管理团队协作，主要由以下几部分组成：

### **main**
项目的主分支，永远保持稳定和可发布的状态。

不接受任何提交，只能从 dev 分支合并而来。

### **dev**
代表了最新的开发进度，功能分支、文档分支都从这里分支出去，最终合并回这里。 

不接受任何提交，只能从其他分支合并。

### **feature**
用于开发新功能。

从 dev 分支创建，开发完成后合并回 dev 分支。

命名规范：feature/feature-name。

### **docs**
用于文档写作。

从 dev 分支创建，开发完成后合并回 dev 分支。

命名规范：docs/docs-name。

## 2.提交规范
本项目参考约定式提交来约束提交内容

每一条提交消息由标头、详情和结尾组成。其中标头具有特殊格式，包含类型、范围和主题：
```text
<类型>[可选 范围]: <描述>

[可选 正文]
```


### 类型
每个提交都必须具有此前缀，它由一个名词构成，诸如 feat 或 fix ，其后接可选的范围字段，可选的 !，以及必要的冒号（英文半角）和空格。
必须是下述类型之一:

* init: 创建项目或子模块时的初始提交
* build: 构建过程或辅助工具的变动
* docs: 文档的更改
* feat: 添加一个新特性
* fix: 修复一个bug
* perf: 提高性能的更改
* refactor: 重构
* style: 不影响代码的更改(空格, 格式化等)
* test: 添加测试

### 范围
范围字段可以跟随在类型字段后面。范围必须是一个描述某部分代码的名词，并用圆括号包围，例如： fix(parser):

### 描述
描述字段必须直接跟在 <类型>(范围) 前缀的冒号和空格之后。描述指的是对代码变更的简短总结

* 使用祈使句，现在时：“change”而不是“changed”也不是“changes”。
* 不要大写第一个字符
* 结尾没有句号(.)

### 正文
在简短描述之后，可以编写较长的提交正文，为代码变更提供额外的上下文信息。正文必须起始于描述字段结束的一个空行后。
提交的正文内容自由编写，并可以使用空行分隔不同段落。

## 3.拉取请求规范
每一个拉取请求 (Pull Request) 由如下结构组成：

标题 (Title): 通常直接复用约定式提交的格式。

摘要 (Summary)：用一两句话简要介绍本次PR的目的和内容。

变更详情 (Changes Made)：清晰列出所有重要的代码变更，如添加的文件、修改的函数等。

破坏性变更 (Breaking Changes)：如有，必须在此处明确列出，并给出迁移或调整的建议。

测试说明 (Testing)：描述你是如何进行测试的，包括单元测试、手动测试步骤或测试用例。

其他注意事项：如性能影响、安全考量、后续待办事项等。

## 4.代码风格与测试
代码风格遵循 `docs/STYLES.md` 和 rust-fmt 配置。

所有新功能必须附带单元测试。
